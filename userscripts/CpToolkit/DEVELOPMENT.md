# CP Toolkit の開発

CP Toolkit を変更する人向けの文書です。利用者向けの説明は [README.md](./README.md) にあります。

## 文書の分担

| 文書                                   | 読者   | 内容                                                     |
|----------------------------------------|--------|----------------------------------------------------------|
| [README.md](./README.md)               | 利用者 | 導入、機能、通信、移行。Greasy Fork の説明文を兼ねます。 |
| [README.en.md](./README.en.md)         | 利用者 | README の英語版。Greasy Fork の英語の説明文を兼ねます。  |
| `docs/features/<機能の ID>.md`         | 利用者 | 機能ごとの詳細。英語版は `.en.md`、画像は `docs/images/` |
| [CHANGELOG.md](./CHANGELOG.md)         | 利用者 | 版ごとの変更内容と、更新時に必要な操作                   |
| [COMPATIBILITY.md](./COMPATIBILITY.md) | 利用者 | 併用できるスクリプトと、併用を推奨しないスクリプト       |
| [SOURCES.md](./SOURCES.md)             | 全員   | 各機能の出典                                             |
| [PERFORMANCE.md](./PERFORMANCE.md)     | 全員   | 旧スクリプトと比べた性能の計測結果の要約                 |
| [bench/README.md](./bench/README.md)   | 開発者 | 性能の計測の手順。版ごとの詳細は `bench/reports/`        |
| この文書                               | 開発者 | 構成、規則、内部の仕様、判断の記録                       |

README は Greasy Fork でも読まれるので、リンクは絶対 URL で書き、HTML は [Greasy Fork で使えるもの](https://greasyfork.org/help/allowed-markup)(表、`<details>`、`<kbd>`、`<sub>` など)に限ります。`align` 属性は Greasy Fork では外れるので、中央寄せは GitHub だけで効きます。Greasy Fork は HTML の要素の中の Markdown を変換しないので、`<div>` と `<details>` の中身は HTML で書きます。表も Markdown ではなく HTML で書きます。Greasy Fork の表には枠線も余白もないので、見出しの行と1行おきの行に `style="background-color: rgba(128, 128, 128, 0.25)"` と `0.1` の背景を付けて縞模様にします(GitHub はこの指定を外し、自前の縞模様を使います)。画像は `raw.githubusercontent.com` の絶対 URL で載せます。見出しは章番号を付け、絵文字は使いません。機能一覧の表は1文に揃え、機能名は詳細ページへのリンクにします。詳しい説明と画像は詳細ページ(`docs/features/`)に置きます。詳細ページは GitHub だけで読むので、Markdown で書いてかまいません。画像は明るい表示で撮り、本文と区別できるよう、1px の枠線(`#d0d7de`)と淡い影を付けて保存します。ユーザー名や所属などの個人の情報が写らない範囲で切り出します。機能を変えたら README、README.en、詳細ページ、設定画面の文言(`data/i18n/`)を揃えます。同じ機能を持つスクリプトが見つかったら COMPATIBILITY に追加します。

## 公開の手順

1. `meta.json` の `version` を、下の「版の付け方」に従って上げます。
2. [変更履歴の書き方](#変更履歴の書き方)に沿って、`CHANGELOG.md` の該当する系列の先頭に、その版の項目を追加します。新しいメジャー版では系列の見出しと目次のリンクを追加し、前の系列との間に水平線（`---`）を入れます。
3. `bun run --cwd userscripts build` で配布物を作り、版番号・変更履歴・配布物を同じコミットに含めます。
4. `main` へ push します。Greasy Fork は `dist/CpToolkit.user.js` の raw URL から同期します。

説明文は配布物とは別に同期します。Greasy Fork の設定に README の raw URL を指定するか、README の変更を貼り付けます。

### 変更履歴の書き方

利用者向けの履歴は日本語の [CHANGELOG.md](./CHANGELOG.md) にまとめます。日本語版・英語版の README ともこの文書へリンクします。

- **記録の単位**は版番号です。前の版から今回の配布物までの変更をまとめ、同じ版を複数回掲載した場合も見出しは1つにします。過去の版を補うときは、Greasy Fork の同じ版番号の最終配布物か、Git にある配布物どうしの差分を確認します。共通コードの変更は、CP Toolkit の利用者に現れるものを拾います。
- **形式**はメジャー版ごとの見出し（`## 3.x`）、版番号（`### 3.0.2`）、日付（日本時間の `YYYY-MM-DD`）、箇条書きの順です。新しい版には `main` で公開する日を書きます。確認できる版別の掲載先があれば、日付の横にリンクを添えます。履歴の訂正やリンクの追記だけなら版は上げません。
- **並び順**は新しい版を上にし、各版の先頭に移行操作、互換性、影響の大きい既定値の変更を置きます。設定の変更や対応する Local Runner が必要なら、誰が何をすればよいかを書きます。
- **表現**は当時の画面にある機能名・ボタン名に合わせ、「〜できるようにしました」「〜する不具合を修正しました」のように書きます。関連する変更は1項目にまとめます。機能名を変えたときは旧名と新名を並べます。

| 変更の種類       | 書く内容                                                                                                                                             |
|------------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| 機能の追加・変更 | 対象のサイトやページと、できるようになった操作を書きます。既定値が変わる場合は新しい動作も示します。                                                 |
| 不具合の修正     | どの機能で、どのような条件で、何が起きていたかを書きます。修正の実装手順は省きます。                                                                 |
| 高速化・最適化   | どの機能や操作を軽くしたかを書きます。計測値や最適化の手法は省きます。                                                                               |
| 削除             | 対象の機能や設定、削除した理由を書きます。代わりに使える操作があれば添えます。過去の理由が記録に残っていない場合は、作者に確認できた範囲で書きます。 |
| 内部整理         | 利用者に見える変更と一緒なら省略します。内部整理だけの版では、対象の機能と操作への影響を1文で示します。                                              |

### 版の付け方

版は `メジャー.マイナー.パッチ` の3つの数で表し、変更の大きさで上げる位置を決めます。上げた位置より右の数は 0 に戻します(1.4.2 の次のマイナーは 1.5.0)。

| 上げる位置 | 対象の変更                                                                                                                                               | コミットの種類の目安 |
|------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------|
| メジャー   | 利用者が設定や使い方を直す必要がある変更。保存した設定を引き継げない形式の変更、機能の削除、旧版からの移行の打ち切り、Local Runner の API の非互換な変更 | 破壊的な変更         |
| マイナー   | 利用者から見える機能の追加と変更。機能や設定項目の追加、既定値の変更、表示や動作の仕様の変更、対応するページの追加                                       | `feat`               |
| パッチ     | 仕様を変えない修正。不具合の修正、性能の改善、見た目の崩れの修正、文言の誤りの修正                                                                       | `fix`、`perf`        |

- 配布物(`dist/CpToolkit.user.js`)が変わる変更では、必ず版を上げます。版が同じだと、Tampermonkey の自動更新で利用者に届きません。
- 文書、テスト、画像だけの変更では上げません。
- 前回の push から次の push までに複数の変更があるときは、その中で最も大きい変更に合わせて1回だけ上げます。機能の追加と不具合の修正を一緒に push するなら、マイナーを1つ上げます。
- 迷ったら、利用者が更新後に何かを新しく知る必要があるかで決めます。知る必要がなければパッチ、新しくできることや変わったことがあればマイナー、設定や使い方を直す必要があればメジャーです。

## 構成

責務ごとに層を分け、各層の中は機能名ではなく領域で分けます。依存は下の図の矢印の向きだけです。

```text
app ──► features ──► application ──► catalog ──► domain ──► shared
 │         └───────► ui
 └───► adapters ──► application
```

| 層            | 置くもの                                        | 使える環境 API              |
|---------------|-------------------------------------------------|-----------------------------|
| `domain`      | 判断と規則                                      | なし                        |
| `catalog`     | YAML を読み込み、型を付けたデータ               | なし                        |
| `application` | 手順とポート(外部とのインターフェース)          | なし                        |
| `ui`          | サイトと機能に依存しない部品                    | DOM                         |
| `adapters`    | ポートの実装。外部との接続                      | DOM、`GM_*`、`unsafeWindow` |
| `features`    | ON/OFF の単位。画面への配置とイベントの接続だけ | DOM                         |
| `app`         | 起動と組み立て                                  | DOM                         |

`application` と `domain` はタイマーも使えません。時間に関わる処理が必要になったらポートを追加します。

迷ったら次の基準で置き場所を決めます。

- 判断や計算は `domain`
- 手順は `application`
- 外部との接続は `adapters`
- 画面への配置は `features`

空の層は作りません。ページ幅の変更のように DOM だけで完結する機能は `features` で閉じます。

## 規則の検査

規則は文書ではなく検査で守ります。

| 規則                   | 検査                                                                                                            |
|------------------------|-----------------------------------------------------------------------------------------------------------------|
| 層の依存方向           | `tsc -b`。各層の `tsconfig.json` の `references` にない層は import できません。                                 |
| 使える環境 API         | `tsc -b`。層ごとの `lib` と `types` にない API は型エラーになります。                                           |
| YAML の形              | `tsc -b`。`catalog` で型に代入できなければ型エラーになります。                                                  |
| 型を消せば JS になる   | `tsc -b`。`erasableSyntaxOnly` により、引数プロパティ、`enum`、`namespace` は型エラーになります。               |
| 機能どうしの独立性     | `tests/architecture.test.ts`                                                                                    |
| 文字列を HTML にしない | `tests/architecture.test.ts`。`innerHTML`、`insertAdjacentHTML`、`eval`、文字列の `setTimeout` などを禁じます。 |
| YAML の内容            | `tests/data.test.ts`。正規表現の妥当性や ID の重複、外部ファイルの版の固定と integrity など                     |

## テストの置き方

テストは `src` と同じ並びに置き、どこを直したらどのテストを見ればよいかを1つに決めます。

| 対象                                      | テストのファイル                                                           |
|-------------------------------------------|----------------------------------------------------------------------------|
| 機能                                      | `tests/features/<機能の ID>.test.ts`。機能ごとに1ファイル                  |
| `domain`、`application`、`adapters`、`ui` | `tests/<層>/<フォルダ>.test.ts`。`src/<層>/<フォルダ>` ごとに1ファイル     |
| `shared` のコード                         | `tests/shared/<ファイル>.test.ts`                                          |
| 全体の規則、データ、配布物                | `tests/architecture.test.ts`、`tests/data.test.ts`、`tests/bundle.test.ts` |

- サービスの代役は `tests/support/fakes.ts`、画面の操作(待つ、キーを押す、カーソルを乗せる)は `tests/support/dom.ts` に置き、各ファイルで作り直しません。
- DOM、`localStorage`、URL、キー操作とツールチップの登録は、`tests/setup/dom.ts` がテストごとに元に戻します。各ファイルで片付けを書かず、前のテストの状態に頼りません。

## データ

人が管理する表はコードに書かず、次の順で考えます。

1. サイトや API から実行時に取れるなら、データとして持ちません。
2. 値だけが変わる表は `data/` の YAML に置きます。
3. 分岐を伴う処理は TypeScript に残します。

CSS は `.css` に分けます。YAML と CSS はビルド時に JS へ同梱されるので、配布物は1ファイルのままです。

YAML の型は `scripts/gen-data-types.ts` が `<name>.d.yaml.ts` として生成します。`typecheck` と `test` が自動で実行し、生成物は Git に入れません。

機能が記憶する値は、以前の版が書いた形のまま残ることがあります。`KeyValueStore` の値はキャストせず、`readStored` と `domain/validation/guards.ts` で形を確かめて読みます。

`@match` は `data/judges/*.yaml` の `matches` から、`@connect` は `data/runners.yaml` と `data/update.yaml` の `connect` から生成するので、`meta.json` には書きません。

コメントの書き方は `data/languages.yaml` にあります。

`data/tessoku.yaml` の難易度は「競技プログラミングの鉄則」の書籍を出典とします。第三者のスクリプトから写したものではありません。

## 機能の追加

1. `src/features/<機能名>/index.ts` で `defineFeature` を使って宣言します。
2. 文言のキーを `data/i18n/ja.yaml` と `en.yaml` に追加します。
3. 対象ページが新しければ `data/judges/*.yaml` の `routes` に追加します。
4. `src/app/registry.ts` に登録します。

貼り付けたコードを加工する機能は、`editor.onPaste` ではなく `paste.add` に登録します。加工の順番が結果に影響するので、`order` の小さいものから順に実行します。

設定画面は `options` の宣言から自動で生成します。

`phase: "ready"` の機能は、サイト自身の `DOMContentLoaded` の処理が終わってから起動します。AtCoder はこの時点で問題文の Copy ボタンや数式の描画を行うので、それより前に DOM を変えないようにします。

`start` が後始末の関数を返す機能は `live: true` を指定できます。ON/OFF と設定変更が再読み込みなしで反映されます。指定しない機能は再読み込みで反映します。

## 内部の仕様

### 判定と Clar の確認

- 提出の直後に一覧のページが開いた時点で最初の確認を行い、以降はサイトが返す `Interval` の間隔で確認します。下限は1秒です。
- 確認の周期は Web Worker のタイマーで作ります。ブラウザが背景のタブのタイマーを間引いても遅れません。
- 別のアプリを操作していても確認を止めません。提出から30分で打ち切ります。
- 確認に失敗すると待ち時間を5秒から倍にしていき、最長で1分にします。
- 確認は1つのタブだけが行います。操作中のタブがあれば、そのタブが確認します。
- Clar の確認はサイトと同じ1分間隔です。

### 通信

`SameOriginHttpClient` は表示中のサイトにしか送りません。外部のサービスは `data/runners.yaml` の `external` に書き、利用者が選んだときだけ使います。内部エラーで次の候補へ切り替わるときも、`external` の実行環境は選びません。

ページの文脈で動くライブラリ(KaTeX、Prettify、Pyodide)は `data/libraries.yaml` と `data/runners.yaml` に置き、npm の版番号か GitHub のコミットの SHA で固定して、integrity で検証します。読み込んだ先でさらに別のファイルを検証なしで読むもの(Prettify の `run_prettify.js` など)は使いません。Pyodide は AtCoder と同じ Python の版の系列から選びます。

### 更新の確認

新しいバージョンがあるかは、導入されたスクリプト自身のヘッダーの `@updateURL` を取得して確かめます(`application/update/update-checker.ts`)。URL をコードに持たないので、GitHub から入れても Greasy Fork から入れても、入れた場所を見に行きます。Greasy Fork は配布のときにこの項目を自分の URL へ書き換えます。

- 取得するのはヘッダーだけ(`Range` で先頭の 8KB)。`@version` を今のバージョンと比べます。
- 通信してよい配布元は `data/update.yaml` の `connect` に書きます。ここに無い配布元から導入した場合は、確かめません。Tampermonkey が接続の許可を求める画面を出さないようにするためです。
- 確認は1日に1回。通信の前に時刻を書き、失敗しても次の間隔まで繰り返しません。
- 知らせるのはバージョンごとに1回。設定画面には、新しいバージョンがある間ずっとリンクを出します。
- 更新は、`@downloadURL` を新しいタブで開くだけ。入れ替えは UserScript の管理ツールが行います。
- ページごとに ON/OFF する機能ではないので、`features` の機能としては登録せず、起動の処理(`app/bootstrap.ts`)と設定画面に組み込みます。

### コードのヘッダーとフッター

- 全文貼り付け時の変換とヘッダーの取得は `PastePipeline` で順に処理し、本文と挿入部分の記録を最後にまとめて反映します。提出ボタンと Easy Test+ は完了を待ちます。
- 複数行コメントがない言語や、閉じる記号を含む文字列では単一行コメントで書きます。
- シェバンのある言語と PHP の `<?php` では、その行の後ろにヘッダーを置きます。PHP の `?>` で終わるコードでは、その前にフッターを置きます。

### Java の変換

`lib.*` の展開は Java Compiler API で構文を解析し、使っている部分だけを取り込む処理です。ブラウザの字句の置換では正しく再現できないので、代わりの処理は持ちません。

### Easy Test+

画面は Shadow DOM の中に作り、ページの `window` には何も公開しません。Codeforces には Bootstrap を読み込みません。

### 旧スクリプトとの違い

Local Runner の既定の URL は `http://localhost:8080` です。利用者に影響する違いは README に書きます。引き継ぎの仕組みは [userscripts/README.md](../README.md#更新を終了したスクリプト) にあります。

## サイトの仕様

次の機能は AtCoder のページが使う仕組みに合わせています。

| 機能                       | 参照したもの                                                                            |
|----------------------------|-----------------------------------------------------------------------------------------|
| 言語の切り替えボタン       | コンテストのページの言語の処理(`#select-lang select.current`、`defaultLang` の記憶)     |
| 提出結果の通知             | コンテストのページの判定待ちの処理(`submissions/me/status/json` と応答の `Interval`)    |
| Clar の通知                | コンテストのページの Clar の処理(`clarifications/count`、1分の間隔、開始直後を避ける)   |
| 提出結果による問題の色分け | 自分の提出一覧(`/contests/<id>/submissions/me`)                                         |
| バーチャル参加             | 参加のページの開始時刻(`#main-container time.fixtime-second`)、ページの `getServerTime` |
| 問題の正誤の色             | AtCoder Problems の表の配色に近い、Bootstrap の `#c3e6cb` と `#f5c6cb`                  |

## 統合しないスクリプト

更新が盛んなもの、サイトやデータの変更への追従が欠かせないものは統合しません。

| スクリプト                                                                     | 理由                                                                            |
|--------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| [AtCoder Easy Test v2](https://greasyfork.org/scripts/433152)                  | CP Toolkit の Easy Test+ は上流から分かれたもので、上流の更新には追従しません。 |
| [ac-predictor](https://greasyfork.org/scripts/369954)                          | 更新が盛んで、サイトの変更への追従が欠かせません。                              |
| [atcoder-difficulty-display](https://greasyfork.org/scripts/397185)            | 更新が盛んで、外部のデータにも依存します。                                      |
| [AtCoderStandingsAnalysis](https://greasyfork.org/scripts/398439)              | 順位表のデータに強く依存し、機能も大きいです。                                  |
| [atcoder-standings-difficulty-analyzer](https://greasyfork.org/scripts/419541) | 順位表のデータに強く依存し、機能も大きいです。                                  |
| AtCoder History Exporter                                                       | 導入しません。                                                                  |
| AtCoder Problems Advanced Summary Exporter                                     | 導入しません。                                                                  |

## コマンド

リポジトリのルートで実行します。

```powershell
bun run --cwd userscripts typecheck
bun run --cwd userscripts build
bun run --cwd userscripts test
```

`test` は配布物も検査するので、先に `build` を実行します。

ブラウザで動きを確かめる手順は [userscripts/README.md](../README.md#ブラウザでの確認) にあります。
