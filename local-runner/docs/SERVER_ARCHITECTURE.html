Local Runner の処理経路と実測

エディタの「実行」から標準出力が返るまで。2026年11月27日、WSL 2 上のサーバーで確認しました。

要求はどこへ届くか

CLI・CP Toolkit → ローカルの Bun サーバーへ HTTP POST
↓
Origin・本文・mode を確認。ソース付きなら言語を選び、同じ準備を待つか、キューに登録します。
↓
Java → 常駐 Dispatcher JVM標準入力・標準出力の専用プロトコルで TRANSFORM → 必要時 COMPILE → 各入力で RUN を送ります。隔離が必要な解答は別の JVM で実行します。
ほかの言語 → Bun が子プロセスを管理設定の bundle とデバッグ変換 → ヘッダー → compile。共有の実行枠が空いた順に、各入力専用の作業フォルダで run のプロセスを起動します。Kotlin のコンパイラや解答が使う JVM もこの経路です。
↓
prepare は programId と完成ソース、run は終了状態・標準出力・標準エラー・計測値を JSON で返します。

CLI は通常、解答を一度 prepare し、各サンプルでは programId と標準入力だけを送ります。Easy Test+ は編集が止まって約180 ms後に precompile を送り、実行ボタンではソース付きの run を送ります。どちらも解答を編集していなければ既に終わった準備を使えます。サンプルの期待出力との照合はクライアント側が担当します。

サーバー起動中に済ませる処理

  1. Bun がポートを確保し、設定を読みます。起動の途中は通常の要求に HTTP 503 と starting を返します。既定ポートは 8080 です。
  2. 設定された Java ライブラリを作業用フォルダに写します。元のソースは利用者のフォルダに残ります。原本の変更を反映するにはサーバーを再起動します。
  3. Java とコマンド言語の準備を並行して行います。Java は配布版の Dispatcher JAR またはソースから作った Dispatcher を使い、ライブラリ索引を作り、ウォームアップ用解答をコンパイルして実行します。
  4. コマンド言語は処理系の場所を確定し、実行時間・メモリ計測用のランチャーを準備します。C++ はデバッグ有効・無効それぞれのヘッダーユニットを用意します。Go の標準パッケージや C# の restore は該当するコマンドがある環境で行います。
  5. 準備が済むと受付状態が ready になります。list は使用可能な言語、status は見つからなかった言語と理由も返します。

Java で「解析を再利用する」とは

たとえば解答に UnionFind uf と書くと、構文解析はこれを変数宣言として木にします。名前解決・型解析は UnionFind がどのパッケージのどの型を指すかを決めます。コンパイラはソース上の開始・終了位置も知っています。Local Runner はこの情報を使って必要なライブラリだけを選び、競プロサイトへ提出できる単一の Main.java を作ります。

時点 実際の処理と再利用の単位
起動時に全ファイルを準備 ライブラリ全体を一括コンパイルし、解答の型解決用の .class を作ります。別の一括 javac タスクでソース、構文木、宣言、位置、型とファイルの対応、ファイル間の依存関係を保存します。バイトコード生成時に javac が構文木を書き換えるため、保持する木を別に用意します。
編集後の初回 prepare 作業用ライブラリのファイル一覧・更新時刻・サイズを確認します。新しい解答の型宣言を調べて仮のファイル名を決め、ライブラリの .class を参照して解答を解析します。解答が使った型から保存済みの依存関係をたどります。
提出ソースの組み立て 選んだ木と元の本文を使い、メインクラス・コンストラクター・衝突する型名・デバッグ変数・import を編集します。改名表は解答ごとに作ります。ライブラリのワイルドカード import の型名集合は索引から引き、解答が宣言を加えたパッケージや型からの import は現在の解答の javac に問い合わせます。
検証と .class 生成 検証指定、改名、複数ファイルの結合などがあれば、展開した Main.java を読み直して参照先・入口を照合します。直近1件の検証済み javac タスクを保持します。完成ソースと検証した全文が一致すれば、次の COMPILE はそのタスクの generate() から進めます。ヘッダー追加などで本文が違えば完成ソースを改めてコンパイルするので、実行結果やスタックトレースの行番号も提出用本文に対応します。
サンプル実行 生成したクラスを確認して隔離の要否を決めます。通常は常駐 JVM 内で解答用のクラスローダーを新しく作り、標準入出力をその要求に接続して main を呼びます。System.exit や Runtime.halt などを参照する解答は専用 JVM を起動します。

JVM の受付は Bun が開く子プロセスのパイプです。追加の HTTP ポートは使いません。タブ区切りの1行に要求種別・ID・フィールドを載せ、ソースや入出力は Base64 にして送ります。JVM の TRANSFORMED・COMPILED・RESULT を Bun が照合し、クライアント向け JSON に変換します。

コマンド言語、設定と PATH

command は主処理系を選ぶ設定です。たとえば g++ なら Bun は起動時に PATH のディレクトリを順に調べて実行ファイルを特定します。絶対パスを指定することもできます。要求時には compile や run の引数配列の {command}・{source}・{output} などを置き換え、そのコマンドを起動します。

「PATH を渡す」とは、子プロセスの環境変数に検索先の一覧を設定することです。主処理系の絶対パスを確定しても、その先で GCC が起動するアセンブラやリンカーの探し方は GCC が決めます。WSL で Linux 版 GCC を直接使う場合に限り、コンパイル用 PATH から Windows ドライブ上の項目を省きます。実際のマウント表で判定するので、ドライブを独自の場所にマウントしても利用できます。実行時の PATH やシステム全体の設定には影響しません。

補助ツールを指定したい場合は GCC の -B/ディレクトリ/ をコンパイル引数に渡せます。この指定はコンパイラ内部の複数の検索にも効きます。独自のラッパーを command に指定する方法もあります。Windows 側の補助ツールを PATH で探す構成では、その言語に "compilePath": "inherit" を設定します。

処理系 既定動作と、時間に影響する理由
C++ / C C++ は -Og にしてコード生成時の最適化作業を減らし、C は -O2 を維持します。両方とも -pipe を使い、中間結果をプロセス間のパイプで渡します。C++ の bits/stdc++.h はコンパイラ・フラグ・コンパイル用 PATH に対応するヘッダーユニットを共有します。高負荷コードで実行性能を優先する場合は compile 配列で -O2 を選べます。
CPython / PyPy 準備ではソースをバイト列として読み、組み込みの compile() で構文とエンコーディングを検査します。py_compile モジュールの起動と .pyc の書き込みを省きます。各入力は従来どおり独立したインタープリターでソースを実行します。
Codon codon build --release の実行ファイルを複数入力で共有します。今回、この既定フラグは変更していません。
Go / Rust Go は起動時に fmt、bufio など標準6パッケージを go build し、以後のビルドで Go 自身のキャッシュを共有します。warmup に [] を設定すると省略できます。Rust は rustc の edition 2024 と -O を使います。-C opt-level=1 も比較しましたが、この測定では合計時間が伸びたため既定値を維持しました。標準ライブラリだけの単一ファイルが対象です。独自の Cargo プロジェクトは compile と run の設定で選べます。
Kotlin 標準の kotlinc 配置ではランタイムの JAR を共有し、解答ごとの JAR へのコピーを省きます。最初の run でマニフェストから main のクラス名を取り、以後は実行引数を再利用します。@file:JvmName でコンパイラが記録したクラスが存在しない場合は javap でエントリーポイントを確認します。共有用 JAR が見つからない配置では設定どおりランタイム同梱で動きます。
C# .NET 9 のプロジェクトを起動中に restore し、各解答は build --no-restore でビルドします。依存解決に使うファイルは共有します。ビルドの中間出力・実行する Main.dll は programId ごとに分け、別の解答のバイナリを使ってしまうことを防ぎます。

HTTP で受け取るもの、返すもの

受け口は同じ URL です。JSON 本文の mode で振り分けます。言語を選ぶ要求で compilerName を省略すると Java を使います。

mode 主な入力 応答とタイミング
list / status mode list は compilerName・family・表示名などの配列、status はサーバーの版、稼働時間、JVM の状態、言語、キャッシュ数などを返します。
header 言語、header 適用する提出用ヘッダーを解決して返します。
precompile ソース、言語、debug 準備キューに登録して accepted を直ちに返します。同じ言語の古い先読みは待ち手がいなければ中断できます。
transform ソース、言語、header、validate など 変換後の sourceCode、diagnostics、inlinedClasses、構造化診断、行のずれなどを返します。実行 ID は発行しません。
prepare ソース、言語、ヘッダー、デバッグ設定など 変換→ヘッダー付与→コンパイルを待ち、成功なら変換情報と programId、失敗なら compileError と診断を返します。同じソース・設定の要求は進行中の準備も共有できます。
run programId またはソース、stdin ID ならコンパイル済みプログラムを起動します。ソースなら準備の完了を待ちます。stdout・stderr・exitCode・time・メモリ・出力切り詰めフラグを返します。結果は success、runtimeError、timeLimitExceeded、compileError などです。期限切れ ID は badRequest です。
shutdown mode accepted を返し、常駐 JVM と HTTP サーバーを停止します。

CLI と同じ2要求の例

{"mode":"prepare","compilerName":"cpython","sourceCode":"print(int(input()) + 1)","header":false}
→ {"status":"success","programId":"…","sourceCode":"print(int(input()) + 1)", …}
{"mode":"run","programId":"…","stdin":"41\n"}
→ {"status":"success","exitCode":0,"stdout":"42\n","stderr":"","time":…,"peakMemory":…, …}

例の応答は主要フィールドだけを示しています。コンパイルや解答のエラーは通常 HTTP 200 の JSON 内の status で判別します。不正な要求は 400、許可されないブラウザ Origin は 403、サイズ上限超過は 413 です。run は HTTP ヘッダーを先に送り、完了後に結果の JSON を送ります。

Python の準備方式だけを交互に切り替えた比較

全言語の比較で CPython の合計が揺れたため、同じサーバーに旧・新の構文検査を設定し、同じ編集について測定順を交互に変えて12組ずつ再計測しました。CPython の準備中央値は 47.79 → 21.19 ms、準備＋3実行は 98.45 → 90.48 ms で、12組中8組で短縮しました。PyPy の準備中央値は 92.65 → 39.81 ms、準備＋3実行は 199.95 → 144.25 ms で、12組とも短縮しました。実行コマンドは各組で同じです。

Java の内部処理を追った別計測

ABC062 D では自作ライブラリの5ファイルが展開されました。別の5編集で、prepare の HTTP 往復は中央値 354 ms、その要求内の COMPILE（Bun のコンパイルログ）は 36 ms でした。各要求でその差を取った中央値は 318 ms で、ソースの展開・検証、キュー、ファイル操作、通信などを含みます。同じソースを独立した transform 要求で検証まで行うと中央値 251 ms でした。この値は別要求なので 36 ms には加算できません。

「OK」と出力するだけのクラスを準備済み ID で5回実行すると、常駐 JVM 経由の HTTP 往復中央値は 3.66 ms（応答内の time は 1 ms）でした。同じ出力の後に System.exit(0) を呼ぶクラスでは、専用 JVM の起動を含めて 48.08 ms（time は 47 ms）でした。

測定条件と読み方

  • Ubuntu 24.04.5 LTS / WSL 2、Bun 1.4.4、OpenJDK 24.0.2、GCC 15.2.0、CPython 3.13.7、PyPy 7.3.20、Codon 0.19.3、Kotlin コンパイラ 2.4.10 を使いました。Python は WSL 側の実行環境です。
  • 変更前は tools のコミット aaa94fd、変更後は作業ツリーです。各版を別の一時ディレクトリ、ホーム、ポートで起動し、HTTP クライアントも WSL 内で動かしました。ベンチマーク用のパスは計測環境だけに設定しました。
  • Java と C++ は ABC062 D の実ファイルを使い、標準入力は 1\n1 2 3\n、期待値は −1 です。Java のライブラリ原本は 224 個の .java を含みます。ほかは整数 1 を読んで 2 を引くプログラムです。Kotlin は package 宣言付きで、別途 @file:JvmName 指定の起動も確認しました。
  • debug を有効にし、提出用ヘッダーを無効にしました。Java は5通り、他言語は3通りの編集コメントを加えて、新しい解答、同じ解答、同じ ID の再実行を区別しました。表の各列に独立して中央値を取るので、内訳の中央値の足し算は合計欄と一致しないことがあります。
  • 返却する time は ms で、コンパイル・キュー待ち・HTTP 転送を含みません。ログの Wait は実行開始までの待ち、Exec は実行、Total はサーバーが受け付けてから結果を出すまでです。常駐 Java の memory は割り当て量を KiB に換算した値です。Linux の計測ランチャーを使う外部プロセスの peakMemory は最大常駐メモリ（KiB）です。

サンプルの並列実行

サーバーが同時に動かすコマンド言語の解答は、run.maxParallelRuns（既定8）と利用可能な論理 CPU 数の小さい方までです。実行枠は CLI と Easy Test+、すべてのコマンド言語で共有します。枠に空きがあれば直ちに解答を起動し、満杯なら先着順に待ちます。待機用のプロセスは起動しません。

大入力は N=50,000～50,015 とし、1～3N の昇順・降順を交互に使いました。期待出力は昇順が −N²、降順が 2N² です。どの設定でも全件 AC でした。別に、公式サンプルで Java 参照解との crosscheck が3件 AC、期待出力を1件書き換えた localtest が1件 WA・2件 AC になることを確認しました。問題文と公式サンプル

ケースを処理する順番

  1. CLI はソースを一度準備し、サーバーが返した実行枠数に合わせて要求します。Java 解答への CLI の要求は解答ごとに1件です。crosscheck は入力ごとに参照解を先に動かし、成功した場合だけ対象解を動かします。異なる入力の処理は重ねられます。
  2. サーバーは待機中もコンパイル結果を保持し、取得した枠でビルド結果をケース専用ディレクトリに複製します。子プロセスの標準入出力、固定名の作業ファイル、計測結果がケースごとに分かれます。実行が終了したら作業フォルダを片付けて枠を返します。コンパイル済み ID の失効が重なった場合、CLI は同じ世代の再準備を共有します。
  3. CLI はケース番号順に詳細を表示し、表示済みの本文を破棄します。先頭が遅いときは表示待ちを含めて枠数の2倍まで先読みします。端末には完了数と判定内訳も表示します。Summary の total は表示したケースの実行時間の合計、wall は全ケースの判定と表示の経過時間です。
  4. 時間制限は各プロセスの実時間にかかります。制限ぎりぎりの解答は1枠で再計測できます。配列やヒープなどを大量に確保する解答では、並列に走るケースの分だけ同時に必要なメモリが増えます。

実装前の比較実験

従来版はコマンド言語の実行と CLI のサンプル判定を直列に処理していました。次の表は試作サーバーに4個の実行枠を設け、同じコンパイル済み解答に8入力を与えたときの HTTP 計測です。

各条件で最初に1ケースを実行し、クライアントの同時 HTTP 要求数を1・2・4と切り替え、測定順をずらして各5組を測りました。 全件欄は組ごとの実時間、各ケース欄は40応答の中央値です。入力は標準入力、出力は全件照合しました。 短い解答は入力に1を加算します。計算主体の解答は入力ごとに異なる初期値から32ビットの線形合同法を C++ で6,000万回、CPython で60万回反復します。 C++ は GCC の -Og -pipe、CPython は WSL の 3.13.7 です。タイムアウトやメモリ上限付近はこの表の計測対象外です。

直列処理の従来版に4件ずつ送る対照実験では、C++ の整数演算が802 ms、CPython の整数入出力が139 msでした（各3組の中央値）。 編集直後はコンパイル時間もかかります。Kotlin の今回の prepare は3,777 msで、準備と8ケースを合わせた目安は4.15秒から3.90秒です。 同じ ID で再テストするときは、表の全件時間の差がそのまま効きます。CPU 周波数やホスト負荷は固定していません。

CPU 競合を確かめるため、サーバーと子プロセスを taskset で同じ1論理CPUに固定し、試験的に4枠を許可しました。 C++ の整数演算は1・2・4並列で全件が768・733・733 ms、各ケースが92・181・352 msでした（各3組）。 Bun の os.availableParallelism() は通常16、同じ固定条件で1を返しました。現在の設定でも、この固定条件では1枠になります。 CPU 使用時間の割当や空きメモリが異なる環境でも4プロセスを支えられるかは別途確認が必要です。
